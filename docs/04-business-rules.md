# 04. Windows 버전에서 반드시 유지해야 할 핵심 업무 규칙

> 이 문서의 규칙은 기존 시스템(`C:\Pjt\kpicCafeteria`)의 코드/테스트에서 확인된 것만 정리한다.
> 코드로 확인되지 않은 사항은 **미확인 사항**으로 명시한다.

## 1. 식단 (Meal Service)

### R1. 배식 생성
- **R1-1**: 배식은 `(service_date, meal_type)` 조합으로 유일하다. 중복 생성 요청 시 기존 배식을 반환한다. (workspace.py `create_service`)
- **R1-2**: 기본 화면에서는 **평일(월~금) 배식만 생성**한다. 주말은 400 에러. (단, 이관/문서 출력에서는 주말 데이터도 처리 가능)
- **R1-3**: 배식 생성 시 `MealTypeSetting`의 `default_planned_count`와 `default_service_time`을 복사한다. (중식 400명/11:40, 석식 100명/17:30 기본값)
- **R1-4**: 배식유형은 `meal_type_settings.active=true`인 코드만 사용 가능하다.

### R2. 계획식수 변경
- **R2-1**: `planned_count` 변경 시 해당 배식의 모든 재료 스냅샷 `quantity_total`을 재계산한다: `quantity_total = quantity_per_100 × planned_count / 100`. (`update_service`)
- **R2-2**: `quantity_per_100`이 NULL인 재료는 재계산하지 않는다.

### R3. 배식 삭제
- **R3-1**: 배식 삭제 시 하위 메뉴/재료 스냅샷/보존식/실제식수는 cascade 삭제된다.

## 2. 메뉴/재료 스냅샷 (Snapshot)

### R4. 메뉴 추가 시 스냅샷 복사
- **R4-1**: 식단에 메뉴를 추가하면 선택한 레시피의 재료를 `MealServiceMenuIngredient`로 **전체 복사**한다. 이후 기준 레시피가 수정되어도 과거 식단 재료는 자동 변경되지 않는다.
- **R4-2**: 스냅샷에는 `ingredient_name_snapshot`(재료명), `quantity_total`, `quantity_per_100`, `unit`을 저장한다. `unit`은 레시피 단위 → 재료 기본단위 순으로 결정한다.
- **R4-3**: `menu_name_snapshot`은 추가 시점의 메뉴명을 복사한다. 메뉴명이 나중에 바뀌어도 식단에는 옛 이름이 유지된다.
- **R4-4**: `recipe_id`/`recipe_name_snapshot`/`recipe_version_snapshot`을 저장해 어떤 레시피를 사용했는지 추적한다.
- **R4-5**: 레시피가 없는 메뉴(예: 물)는 재료 스냅샷 없이 추가 가능하다.

### R5. 레시피 변경
- **R5-1**: 식단 메뉴의 레시피를 변경하면 기존 재료 스냅샷을 **전체 삭제 후 새 레시피 재료로 재복사**한다. (교체 방식, 병합 아님)
- **R5-2**: 레시피 선택 규칙: 명시된 `recipe_id` → 활성 레시피 중 `is_default` → 활성 레시피 중 첫 번째 → 없으면 None. (`_select_recipe`)
- **R5-3**: 다른 메뉴의 레시피를 지정하면 400 에러.

### R6. 재료 스냅샷 수동 편집
- **R6-1**: 재료 스냅샷 편집은 전체 교체 방식(delete + insert)이다.
- **R6-2**: `quantity_total`만 입력하면 `per_100 = total × 100 / planned_count`로 역산한다. `quantity_per_100`만 입력하면 `total = per_100 × planned_count / 100`로 계산한다.
- **R6-3**: 재료 ID 없이 이름만으로도 스냅샷 저장 가능 (`ingredient_id=NULL` + `ingredient_name_snapshot`). 삭제된 재료의 스냅샷이 이 형태로 남는다.

### R7. 대표 메뉴
- **R7-1**: 배식당 대표 메뉴(`is_representative`)는 최대 1개.
- **R7-2**: 메뉴 추가 시 첫 번째 `주찬` 메뉴에 자동 지정된다.
- **R7-3**: 일괄 저장 시 여러 메뉴가 True면 **첫 번째 True만 승인**된다. 해제는 가능.

## 3. 레시피 (Recipe)

### R8. 다중 레시피
- **R8-1**: 같은 메뉴에 재료 구성이 다른 여러 레시피를 등록할 수 있다.
- **R8-2**: 레시피 구분 키 `composition_key` = **재료 ID 집합을 정렬해 `,`로 결합**한 문자열. 빈 구성은 `"EMPTY"`.
- **R8-3**: **수량과 단위는 composition_key에 포함되지 않는다.** 재료 구성이 같고 수량만 다른 경우 새 레시피를 만들지 않고 기존 레시피를 수정한다.
- **R8-4**: 같은 메뉴에 같은 composition_key의 레시피 중복 등록은 409 에러.
- **R8-5**: 버전은 메뉴별 순차 증가 (1, 2, 3...).
- **R8-6**: `is_default`는 메뉴당 1개. 기본 레시피를 비활성화하면 활성 레시피 중 버전 순으로 대체 지정.
- **R8-7**: 레시피 삭제는 미사용 처리(`active=false`)이며 `is_default=false`로 변경한다.
- **R8-8**: 레시피에 없는 재료명이 입력되면 `stat_group="기타"`, `review_status="자동등록-분류필요"` 상태로 재료를 자동 생성한다.
- **R8-9**: 레시피 내 같은 재료 중복 입력은 400 에러.

### R9. 레시피 재료 수량
- **R9-1**: 레시피 재료 수량은 **100인 기준**(`quantity_per_100`)이다.
- **R9-2**: 단위 미지정 시 재료의 `default_unit`을 사용한다.

## 4. 발주량 계산 (Order)

### R10. 필요량 집계
- **R10-1**: 발주 필요량은 **식단 스냅샷의 `quantity_total`**을 (사용일, 재료) 기준으로 합산한다. 같은 날짜에 여러 메뉴가 같은 재료를 쓰면 합산된다.
- **R10-2**: `quantity_total`이 NULL인 재료는 집계에서 제외한다.
- **R10-3**: `ingredient_id`가 없는 재료는 `"name:{이름}"` 키로 구분한다 (삭제된 재료도 집계 유지).
- **R10-4**: 사용일별로 별도 행이 생성된다. (날짜 간 합산 아님)

### R11. 발주량 기본값
- **R11-1**: 신규 발주 항목의 `order_quantity` 기본값 = `required_quantity`.
- **R11-2**: 기본 발주일 = `service_date - 1일`, 기본 배송일 = `service_date`.

### R12. 사용자 입력 보존
- **R12-1**: 발주 항목 저장은 (사용일, 재료) 기준 upsert. 사용자가 입력한 `order_quantity`/`order_unit`/`order_date`/`delivery_date`/`status`는 식단이 변경되어도 **덮어쓰지 않는다**.
- **R12-2**: `required_quantity`는 항상 최신 식단 기준으로 표시된다 (사용자 입력 아님).
- **R12-3**: 식단에서 사라진 재료의 발주 항목도 **삭제하지 않고** `in_plan=false`로 유지한다. (사용자 입력 무시 금지 원칙)

### R13. 발주 상태
- **R13-1**: 상태값은 `pending`(미처리) / `ordered`(발주완료) / `skipped`(발주안함) 3개만 허용.
- **R13-2**: 묶음 발주 생성 시 그룹에 속한 항목은 `status=ordered`로 변경되고 `order_date`/`delivery_date`가 그룹 값으로 동기화된다.
- **R13-3**: 묶음 발주 그룹의 `total_required_quantity` = 항목 `required_quantity` 합계.

## 5. 실제 식수 (Meal Actual)

### R14. 실제 식수
- **R14-1**: 실제 식수는 보존식 기록과 **독립적으로 저장**된다. (1:1 관계, 별도 테이블)
- **R14-2**: `actual_count` 입력 시 `recorded_at`이 기록된다. 값을 비우면 `recorded_at`도 NULL.
- **R14-3**: `actual_count`는 0 이상 정수만 허용.

### R15. 식수 통계 규칙
- **R15-1**: 이상치 판정 기준: 계획 대비 또는 평소 대비 편차가 **±10% 이상이면 "확인", ±15% 이상이면 "중요"**.
- **R15-2**: 평소 값 = 해당 배식일 이전 56일 중 같은 meal_type의 실제 식수 **중앙값**. 비교 데이터 4건 미만이면 평소 대비 판정 제외(`insufficient_comparison`).
- **R15-3**: 편차율 = `(actual - base) / base × 100` (base ≤ 0이면 None).
- **R15-4**: 지연 입력 판정: `recorded_at`의 날짜 - `service_date` > 1일이면 지연.

## 6. 조리지시서 (Cooking Instruction)

### R16. 조리지시
- **R16-1**: 조리지시(`cooking_instruction`)와 조리비고(`cooking_note`)는 **메뉴별 필수 입력이 아니다**. 비어 있어도 저장/출력 가능.
- **R16-2**: 문서 출력 시 비고는 `cooking_note` 우선, 없으면 `note`(메뉴 비고)를 사용한다.
- **R16-3**: 조리지시서 출력 시 해당 배식의 `cooking_output_at`이 기록된다. (주간 카드에 출력 여부 표시)

### R17. 조리지시서 문서 규칙
- **R17-1**: 일자별 중식/석식 블록 구성. 중식이 석식보다 먼저.
- **R17-2**: 메뉴당 최대 7개 슬롯. 7개 초과 메뉴는 마지막 슬롯에 나머지를 병합 표시.
- **R17-3**: 재료 표시 형식: `재료명 수량단위` (예: `돼지고기 18kg`). 수량/단위가 없으면 재료명만.
- **R17-4**: 조리지시는 재료 목록 다음 줄에 표시. 비고는 파란색(별도 charPr)으로 구분.

## 7. 보존식 기록 (Preservation Record)

### R18. 보존식 기록
- **R18-1**: 배식당 1건 (1:1). 채수일시/관리자/냉동고온도/폐기일시/채수자/채수시간/비고.
- **R18-2**: `completed` 체크 시 `completed_at` 기록, 해제 시 NULL.
- **R18-3**: 냉동고 온도와 채수시간은 **문자열**로 저장 (형식 검증 없음).

### R19. 보존식 기록지 문서 규칙
- **R19-1**: 한 페이지에 **3건** 배치. 부족한 칸은 빈 양식으로 유지 (페이지 수 = ceil(식수/3)).
- **R19-2**: 정렬은 (서비스 날짜, 중식→석식) 순서.
- **R19-3**: 기록이 없는 배식도 빈 블록으로 출력된다 (누락이 아니라 빈 양식).

## 8. 기간/주 단위 처리

### R20. 주간 화면
- **R20-1**: 주 시작은 월요일. `week_start`가 주중이면 그 주의 월요일로 보정.
- **R20-2**: 기본 2주 표시, 1~8주 범위.
- **R20-3**: 평일 5열만 표시 (주말 열 없음, 빈 공간 없음).

### R21. 주차 라벨 (문서)
- **R21-1**: "X월 Y주" 라벨 규칙: **월 1일이 월~금이면 그 주가 1주, 토~일이면 다음 주가 1주**.
- **R21-2**: 기간 라벨: 같은 주면 "8월 3주", 같은 달이면 "8월 3~4주", 다른 달이면 "8월 3주~9월 1주".

## 9. 이관 (Migration)

### R22. XLSX 이관
- **R22-1**: 필수 시트 7개: `01_배식설정` / `02_메뉴기준정보` / `03_재료기준정보` / `04_재료별칭_선택` / `05_메뉴별재료_기준` / `06_식단이력_이관` / `07_식단재료_이관`.
- **R22-2**: `replace` 모드는 업무 데이터 전체 삭제 후 재구축. **사용자/문서 템플릿/감사 로그는 보존**.
- **R22-3**: 레시피는 sort_order 역전(블록 경계)을 기준으로 재료 구성 블록을 분리해 composition_key로 그룹핑.
- **R22-4**: 과거 식단 재료는 당시 수량(`quantity_total`)을 스냅샷으로 보존하고 `quantity_per_100 = total × 100 / planned`로 역산.
- **R22-5**: 수량/단위가 비어 있어도 이관하며 통계 중량값만 제외. 임의로 값을 채우지 않는다.
- **R22-6**: Excel 날짜는 1900 날짜 시스템 기준 `date(1899,12,30) + serial`로 변환.

## 10. 문서 출력 공통

### R23. 출력 규칙
- **R23-1**: 식단표/조리지시서 출력 시 배식의 `meal_plan_output_at`/`cooking_output_at` 기록.
- **R23-2**: 문서 파일명: `식단표_YYYYMMDD_YYYYMMDD.hwpx` / `조리지시서_YYYYMMDD_YYYYMMDD.hwpx` / `보존식기록지_YYYYMMDD_YYYYMMDD.hwpx` (단일 날짜면 `_YYYYMMDD`).
- **R23-3**: 미리보기 토큰은 6시간 만료, 사용자 소유 검증.
- **R23-4**: HWPX 템플릿은 유형당 1개 활성. 활성 템플릿 없으면 409.
- **R23-5**: HWPX 생성 후 `{{...}}` 플레이스홀더가 남아 있으면 실패 처리.

## 11. 사용자/권한

### R24. 사용자 규칙
- **R24-1**: 비밀번호 최소 8자, 사용자 ID와 동일 금지.
- **R24-2**: 신규 사용자/비밀번호 초기화 시 `must_change_password=true`.
- **R24-3**: 본인 계정 비활성화 금지.
- **R24-4**: 시스템에는 최소 1명의 활성 admin이 필요 (권한 변경/비활성화 시 검증).
- **R24-5**: admin 전용 화면: 사용자 관리, 백업, 아카이브.

## 12. 미확인 사항

- **M1**: `is_representative`가 문서 출력(식단표/조리지시서)에 어떤 영향을 주는지 — 코드에서 문서 payload에 포함되지 않음 (미사용으로 추정)
- **M2**: `review_status` 값의 전체 목록과 의미 (정상/자동등록-분류필요 외) — 이관 데이터에 따라 다름
- **M3**: `kg_factor`의 정확한 사용처 — `stats_service.py`에서만 사용 (g→kg 환산). 다른 단위 환산 규칙은 미확인
- **M4**: 주말 배식 데이터가 존재할 때 문서 출력/통계에서의 처리 — 코드상 평일 가정이 없어 동작은 하나, 화면에서 주말 배식 생성이 불가능한 것만 확인
- **M5**: `collection_time`과 `collected_at`의 관계 — 별도 필드로 저장되며 문서에서 각각 사용 (채수시간 문자열 vs 채수일시)
- **M6**: 메뉴 역할(`role`) 코드 목록은 `master.py::MENU_ROLES`에 하드코딩되어 있으나, DB에는 자유 문자열로 저장 가능 (이관 데이터의 역할 값과 일치 여부 미확인)
